# Mobile auth bearer token extraction

The registration bug fix extracts bearer tokens from Better Auth for mobile client authentication. The change implements `asResponse: false` on `signUpEmail` and `signInEmail`, adds token extraction logic with a DB fallback, wraps Patulod user creation in a transaction, and types the session response explicitly.

The approach is sound: when Better Auth returns `result.token` directly, use it and fetch `expiresAt` from the DB; when it doesn't, fall back to querying the session table for both fields. The transaction wraps Patulod DB operations but can't include Better Auth (separate connection), leaving a gap where Better Auth users can be orphaned if the transaction fails. The `AuthResponse` interface now explicitly types `session` as `{ token: string; expiresAt: string }`, matching mobile expectations.

## High-level view

Both `registerPassenger` and `loginPassenger` now call Better Auth with `asResponse: false`, extract the token from `signUpResult.token` if present, and fall back to querying `db.session.findFirst` ordered by `createdAt desc` when it's not. The fallback query retrieves both `token` and `expiresAt` when needed, or just `expiresAt` when the token is already available.

The transaction wraps `patulodUser`, `termsAcceptance`, `privacyAcknowledgment`, and `auditLog` creation, correctly excluding the Better Auth `signUpEmail` call. If any Patulod DB operation fails, the transaction rolls back, but the Better Auth user remains (this is by design since Better Auth uses its own connection).

The `AuthResponse.session` field is explicitly typed as `{ token: string; expiresAt: string }`, replacing the previous permissive typing. Error handling logs the full context when session data is missing and returns descriptive messages to the client.

## Transaction boundary leaves orphaned Better Auth users

The `registerPassenger` function wraps four DB operations in a transaction:

```typescript
await db.$transaction(async (tx) => {
  const patulodUser = await tx.patulodUser.create({ ... })
  await tx.termsAcceptance.create({ data: { userId: patulodUser.id, ... } })
  await tx.privacyAcknowledgment.create({ data: { userId: patulodUser.id, ... } })
  await tx.auditLog.create({ data: { userId: patulodUser.id, ... } })
})
```

The Better Auth `signUpEmail` call is placed outside the transaction. Better Auth manages its own database connection, so it can't participate in the Prisma transaction.

If the transaction fails after Better Auth creates the user, the Better Auth user record exists but no Patulod user record is created. The user can log in (Better Auth succeeds), but any Patulod-specific operations will fail when they look up `patulodUser` by `userId` and find nothing. The error handling returns `{ success: false, error: 'Failed to create account. Please try again.' }`, but the Better Auth user remains in the DB. This is acknowledged as a known trade-off in the plan.
